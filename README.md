# Digital Twin Beam Prediction — Environmental Shift Extension

This repository is an extension of the original codebase for:

> S. Jiang and A. Alkhateeb, "[Digital Twin Based Beam Prediction: Can we Train in the Digital World and Deploy in Reality?](https://arxiv.org/abs/2301.07682)," arXiv preprint arXiv:2301.07682 (2023).

**If you are new to this repo, read this file top to bottom once. It explains what the original paper did, what our thesis adds on top of it, where every file lives, and exactly how to re-run everything from scratch.**

---

## 1. The original work this repo builds on

The original paper's idea: instead of collecting thousands of real-world measurements to train a beam-prediction model at every new cell site, build a **digital twin** — a simulated, ray-traced version of the site — and train the model on synthetic data from that twin. Then fine-tune the model with just a handful of real measurements. The original paper's abstract:

> Realizing the potential gains of large-scale MIMO systems requires the accurate estimation of their channels or the fine adjustment of their narrow beams. This, however, is typically associated with high channel acquisition/beam sweeping overhead that scales with the number of antennas. Machine and deep learning represent promising approaches to overcome these challenges thanks to their powerful ability to learn from prior observations and side information. Training machine and deep learning models, however, requires large-scale datasets that are expensive to collect in deployed systems. To address this challenge, we propose a novel direction that utilizes digital replicas of the physical world to reduce or even eliminate the MIMO channel acquisition overhead. In the proposed digital twin aided communication, 3D models that approximate the real-world communication environment are constructed and accurate ray-tracing is utilized to simulate the site-specific channels. These channels can then be used to aid various communication tasks. Further, we propose to use machine learning to approximate the digital replicas and reduce the ray tracing computational cost. To evaluate the proposed digital twin based approach, we conduct a case study focusing on the position-aided beam prediction task. The results show that a learning model trained solely with the data generated by the digital replica can achieve relatively good performance on the real-world data. Moreover, a small number of real-world data points can quickly achieve near-optimal performance, overcoming the modeling mismatches between the physical and digital worlds and significantly reducing the data acquisition overhead.

The original result: a model pretrained purely on synthetic digital-twin data gets **91.4% top-2 beam prediction accuracy** on real data with zero real samples, and fine-tuning it with fewer than 20 real samples closes almost the entire remaining gap.

## 2. What our thesis adds on top of this

The original paper only ever tested one thing: a digital twin built once, deployed once, at one site, at one point in time. It never asked: **what happens after deployment, when the real environment itself changes?**

Our thesis asks exactly that question, along two realistic axes:

1. **Time-of-day** — does the model still work at night if it was only ever tuned during the day (same street)?
2. **Site** — does the model still work on a different street, one it was never tuned for?

And specifically: if a model has already been deployed and fine-tuned with a bit of real data (the original paper's recipe), and *then* the environment shifts, **how badly does it break, and how much new real data does it take to fix it?**

**The short answer we found:** time-of-day shift is a real but mild problem that a modest amount of new real data fixes efficiently. Site shift is a severe problem — sometimes the model performs *worse than random guessing* — and needs far more real data to even partially recover. Full numbers are in [Section 8](#8-key-findings-plain-language).

## 4. The data

### 4.1 `dataset/` — the four DeepSense6G scenarios (raw, real-world)

All real measurement data used by the new work comes from [DeepSense 6G](https://www.deepsense6g.net/), a public real-world dataset. We use four scenarios that, between them, form a clean **2×2 design**: two physical streets, each recorded in daytime and nighttime conditions.

| Scenario | Location | Time of day | Samples |
|---|---|---|---|
| 1 | McAllister Ave., Tempe, AZ | Day | 2,411 |
| 2 | McAllister Ave., Tempe, AZ (same street as 1) | Night | 2,974 |
| 3 | Rural Road, Tempe, AZ | Day | 1,487 |
| 4 | Rural Road, Tempe, AZ (same street as 3) | Night | 1,867 |

Each scenario folder contains, per recorded moment: a camera photo (`unit1/camera_data/`, not used by our pipeline), the base station's fixed GPS location (`unit1/GPS_data/`), the vehicle's GPS location at that moment (`unit2/GPS_data/`), and a text file with the 64 raw beam-power measurements from that moment (`unit1/mmWave_data/`). A `scenarioN.csv` file in each folder indexes all of this.

**Important:** `dataset/` is listed in `.gitignore` — it is not tracked by git because it's large. If you don't have it locally, you need to obtain it separately (from DeepSense6G directly, or from whoever on the team already has it) before you can run the preprocessing step.

### 4.2 `data/` — preprocessed, ready-to-train data

This is what `preprocess_position_and_beam.py` produces from the raw `dataset/` folder (see [Section 6.1](#61-phase-0--preprocessing)). It includes:

- `scenarioN_ue_relative_pos.mat`, `scenarioN_real_beam_pwr.mat`, `scenarioN_ue_gps_pos.mat` for each of the four scenarios — position and beam-power data, ready for the model.
- `scenarioN_ue_scatter.png` — a bird's-eye-view sanity-check plot for each scenario (base station at the origin, every recorded vehicle position plotted around it).
- `scenario_preprocessing_summary.json` — sample counts and estimated base station orientation (in degrees) for each scenario.
- `global_normalization.json` — the shared position-normalization constants (`max_xy`, `max_dist`) computed by pooling all four scenarios together, so that a given normalized position value means the same physical distance regardless of which scenario it came from.
- `real_beam_pwr.mat`, `ue_relative_pos.mat`, `ue_gps_pos.mat` (no scenario prefix) — this is the **original** paper's own Scenario 1 data, used only for the Stage 0 reproduction. Do not confuse this with `scenario1_*` above, which is our own re-preprocessed version of the same underlying scenario.

### 4.3 `archive/` — the original synthetic digital-twin data

The original paper's approach needs one more ingredient we haven't mentioned yet: **synthetic digital-twin data** — a ray-traced simulation of McAllister Ave, used to pretrain the model with zero real data (this is what makes it a "digital twin" paper). These files (`deepsense_s1_synth_v3_interval_0p1.mat` and related) are **only needed for Stage 0** (the reproduction of the original paper's result) — our new Stage 1 work is entirely real-to-real and never touches synthetic data at all.

These files are large and have been moved out of `data/` into an `archive/` folder that currently lives **outside this repo**, kept safe separately. If you need to re-run the Stage 0 reproduction (`train_model_synth_measured.py`, `train_model_synth_uniform.py`, `train_model_transfer_learning_measured.py`, `train_model_transfer_learning_uniform.py`, `train_model_real.py`, or `train_model_real compare_with_transfer_learning.py`), you must first copy that `archive/synthetic_stage0_data/` folder back into the repo root — every one of those scripts expects to find it at exactly that path. **Ask whoever has the backup for a copy before trying to run any of those six scripts.**

## 5. The model

One model architecture is used throughout the original paper's work and Stages 0–1 of our extension. It's deliberately simple: a small fully-connected neural network (defined in `original_project/model.py`) that takes a 4-number description of the user's position (x, y, angle, and distance relative to the base station) and outputs a probability for each of 16 possible beams.

```
Input (4 numbers: x, y, angle, distance)
   -> Linear(4 -> 256) -> ReLU
   -> Linear(256 -> 256) -> ReLU
   -> Linear(256 -> 256) -> ReLU
   -> Linear(256 -> 16)   [one score per beam]
```

A later follow-up (`model_comparison_study/`, see Section 6.5) compares this architecture against 6 alternatives — cheaper and more expensive neural variants, plus two non-neural baselines — on the same Stage 1 protocol, to find the best accuracy-per-resource-cost tradeoff.

Why 16 beams when the hardware sweeps 64? The real antenna hardware only actually has 16 physical beam directions; the extra 64-value sweep is an oversampled research measurement. Every script in this repo picks out the correct 16 out of 64 using the same rule (`beam_pwr[:, 1::4]` in `data_feed.py`), which is a property of the hardware itself and is identical across all four scenarios.

## 6. The pipeline, step by step

### 6.1 Phase 0 — Preprocessing

**Script:** `original_project/preprocess_position_and_beam.py`
**Run from the repository root** (this matters — see the warning box below):
```bash
python original_project/preprocess_position_and_beam.py
```

What it does, for each of the four scenarios in `dataset/`:
1. Reads every recorded GPS position and converts it from raw latitude/longitude into plain "meters from the base station," using the standard UTM map-projection method.
2. Reads every recorded 64-value beam-power sweep and finds which beam was strongest at each moment (the "correct answer" the model will learn to predict).
3. Estimates which physical compass direction the base station's antenna is actually pointed, purely from the data itself: it looks at every moment where beam #28 (the antenna's designated "straight ahead" beam) happened to be the correct answer, and fits a line through those positions.
4. Saves everything to `data/`, plus a sanity-check scatter plot per scenario, plus the pooled global normalization constants described in Section 4.2.

> ⚠️ **Every script in this repo must be run with your terminal's current folder set to `digital_twin_extended` itself (the repo root), not `original_project/` or `model_comparison_study/`.** All the file paths inside these scripts (like `data/scenario1_ue_relative_pos.mat`) are written relative to the repo root. Running a script from inside its own folder will make it silently fail to find its own data — this bit us multiple times during development, so it's worth over-emphasizing.

### 6.2 Stage 0 — Reproducing the original paper's result

**Scripts:** `original_project/train_model_synth_measured.py`, `train_model_transfer_learning_measured.py`, and their `_uniform` counterparts, plus `train_model_real.py`.

This step exists purely to **prove our implementation is correct** before trusting any new result built on top of it — it doesn't test anything new. It pretrains the model on synthetic digital-twin data (see Section 4.3 — you need the `archive/` folder restored for this), then fine-tunes it on a small, increasing number of real McAllister Ave samples, exactly reproducing the original paper's experiment.

```bash
python original_project/train_model_transfer_learning_measured.py
```

**Result we obtained:** 91.53% top-2 accuracy with zero real samples (the original paper reports 91.4% — a match within 0.13 percentage points), climbing to 97.83% with 100 real samples.

### 6.3 Stage 1 — Our new contribution: does this survive environmental change?

**Script:** `original_project/train_model_cross_scenario.py` (new, written for this thesis)

This is the core new experiment. For each of four comparisons built from the scenarios in Section 4.1, it trains a model from scratch on one scenario ("source"), tests it immediately (zero real target samples) on a different scenario ("target"), then fine-tunes it on a growing number of real target samples (5, 10, 15, ... up to 200) and re-tests after each step.

```bash
python original_project/train_model_cross_scenario.py
```

The four comparisons (each changes exactly one thing — either time-of-day or site, never both):

| Comparison | What changes | What stays the same |
|---|---|---|
| Scenario 1 → 2 | Time of day | Site (McAllister) |
| Scenario 3 → 4 | Time of day | Site (Rural Road) |
| Scenario 1 → 3 | Site | Time of day (Day) |
| Scenario 2 → 4 | Site | Time of day (Night) |

This uses only real data throughout — no digital twin, no ray tracing, no `archive/` folder needed. It runs 10 independent random repeats per comparison (started at 5, doubled to 10 after we found the smaller number gave an unreliable answer for one comparison — see Section 8). On a normal CPU-only machine, expect this to take roughly 25–30 minutes for all four comparisons.

### 6.4 Diagnostic — is it really about more data, or just more training time?

**Script:** `original_project/train_model_epoch_ablation.py` (new, written for this thesis)

A fair question about Stage 1's results: when we give the model more real samples, we're also giving it more training batches per epoch, so it's technically training *longer* too — how do we know it's the extra data that matters, and not just extra training time? This script isolates that: it fixes the real-sample count at exactly 100 for every comparison, and only changes how many epochs it fine-tunes for (40 vs. 80 — roughly matching the extra training time that going from 100 to 200 samples would provide).

```bash
python original_project/train_model_epoch_ablation.py
```

**Result:** doubling the epoch budget alone changes accuracy by less than 0.1 percentage points across every comparison. It's genuinely about having more real data, not about training for longer.

### 6.5 Model comparison study — which architecture is most efficient?

**Folder:** `model_comparison_study/` (new, written as a follow-up to the thesis's Stage 1 result)

The original paper, Stage 0, and Stage 1 above all use one fixed architecture — a 3-hidden-layer MLP (`FullyConnected` in `model.py`). This follow-up study asks a different question: which of a handful of alternative, cheap-to-train models gives the best accuracy *per unit of resource cost* on the exact same Stage 1 cross-scenario protocol (same four scenarios, same splits, same sweep of real target samples)? See `model_comparison_study/model.py` and `model_comparison_study/train_baselines_cross_scenario.py` for full docstrings and rationale per model.

(Two more expensive variants — a residual MLP with LayerNorm/dropout, and a tabular transformer with self-attention over the 4 features — were tried and dropped. Neither changed the picture enough to justify the extra training cost, and dropping them keeps every model in this comparison in the same cheap, fast-to-run tier.)

| Model | Type | Params | Run with |
|---|---|---|---|
| `mlp` | Original `FullyConnected` (reference point) | 136,976 | `python model_comparison_study/train_model_cross_scenario.py --model mlp` |
| `tinymlp` | 2-layer, 32-unit MLP | 1,744 | `--model tinymlp` |
| `knn` | k-Nearest Neighbors | — | `python model_comparison_study/train_baselines_cross_scenario.py --model knn` |
| `rf` | Random Forest | — | `--model rf` |
| `fourier_knn` | k-NN on NeRF/SIREN-style sinusoidal position features | — | `--model fourier_knn` |
| `fourier_rf` | Random Forest on the same sinusoidal position features | — | `--model fourier_rf` |

(A neural `fouriermlp` variant — the same sinusoidal encoding feeding the `FullyConnected` backbone instead of a tree/geometric model — was tried and dropped: it inherits the same source-pretrain/target-finetune weakness that `knn`/`rf` already show dominates the plain MLP, and its full run took too long for the marginal insight it would add. `fourier_knn`/`fourier_rf` test the same "does spatial encoding help" question directly on the models that already outperform the MLP, for a fraction of the cost.)

Each run prints parameter count and wall-clock training time alongside accuracy, and writes to `result/stage1_<comparison>_<model>_acc.mat` / `_pwr.mat` / `result/stage1_summary_<model>.json` — suffixed so nothing overwrites the original `mlp` results from Section 6.3. `knn` and `rf` don't have a gradient-based fine-tuning mechanic, so each real-sample sweep point is a fresh fit on the available target data rather than a continued one; see the docstring at the top of `train_baselines_cross_scenario.py` for the exact protocol difference this implies.

## 8. Key findings (plain language)

1. **We reproduced the original paper correctly.** 91.53% vs. their published 91.4% — a near-exact match, confirming our whole pipeline works as intended before we changed anything.
2. **Time-of-day shift is a real problem, but a manageable one.** At McAllister Ave, a model trained only during the day still gets 48% accuracy at night with zero new data, and climbs to 66% with 200 real night samples.
3. **Site shift is a much bigger problem.** Moving the same kind of model to a different street can push accuracy *below what random guessing would achieve* (as low as 0.4%, against a 12.5% random-guess baseline) — meaning the model isn't just "unsure," it's confidently giving wrong answers. It takes on the order of 150–200 real samples before recovery even becomes visible, and even then it only climbs back to roughly the random-guess level, nowhere near what the time-of-day case achieves with the same amount of data.
4. **This recovery is genuinely about having more real data — not just more training time.** Confirmed directly by the epoch-ablation diagnostic in Section 6.4.
5. **A word on scientific honesty:** our first pass at Stage 1 used only 5 repeats per comparison, and it looked like the site-shift case had actually recovered past the random-guess baseline. Doubling to 10 repeats corrected that — the honest number is that it recovers to *roughly* the random-guess level, not above it. We're documenting this correction openly because it's a better, more defensible finding than the uncorrected one, and because it's exactly the kind of thing a careful reader should be able to see was checked, not glossed over.

Our best current explanation for *why* site shift is so much worse: the two streets' base station antennas are very likely mounted at different physical compass orientations (our own estimates put them roughly 6–13 degrees apart), so the same beam number points in a different real-world direction at each site. A model trained at one site learns a confident, smooth rule connecting position to beam number — and that exact rule becomes actively wrong, not just unfamiliar, at a site with a different antenna orientation. This is a plausible, evidence-consistent explanation, but not yet directly proven — see Section 9.

## 9. Known limitations

- Only two physical sites were tested (McAllister Ave and Rural Road). We don't yet know if the size of the site-shift effect would be the same, bigger, or smaller between a different pair of streets.
- The orientation-mismatch explanation above is our best current theory, consistent with what we measured, but we haven't run the direct test that would confirm it (rotating target-site positions by the estimated orientation difference before evaluating, to see if that recovers some accuracy).
- The base station orientation estimate for Rural Road rests on very few samples (8–9), compared to McAllister's 18–60, because the estimation method can only use moments where the measured best beam exactly matched the antenna's designated "straight ahead" beam.
- Stage 1 uses 10 random repeats per comparison; the original paper's own experiments (and our Stage 0 reproduction of them) use 30. We showed in Section 8 that this choice genuinely matters, so treat the Stage 1 numbers as good-but-not-maximally-tight estimates.
- Everything was trained on CPU only; given how small this model and dataset are, that was never a speed bottleneck.

## 10. Suggestions for next steps

- **Model experiment (in progress on a separate branch):** the original model defines a dropout layer that is never actually used in its `forward()` method — literally dead code. Enabling it is a cheap, well-motivated test of whether regularizing against overconfident predictions softens the site-shift collapse, which would be direct evidence for the orientation-mismatch theory above.
- Directly test the orientation-mismatch theory (see Section 9).
- Add a third physical site, to see if the site-shift finding replicates with a different, independent pair of streets.
- Try the rehearsal-based fine-tuning and informative-sample-selection techniques from the wider digital-twin literature (mixing old and new data during fine-tuning, rather than fine-tuning on new data alone) to see if they narrow the site-shift recovery gap.
- Increase the Stage 1 repeat count from 10 toward 30, to match the confidence level of the Stage 0 reproduction.
